## Problem Statement

field-radar already harvests 460,585 arXiv computer-science papers (Nov 2023 to Nov 2026), embeds 459,249 of them with SPECTER2 vectors (768 numbers per paper, from Semantic Scholar), clusters them into a three-level map (20 / 116 / 368 clusters), scores rising phrases, and writes a monthly report plus two static pages (`report/map.html`, 36 MB; `report/merge.html`). The outputs can be read but not questioned: the time window, the home field and every table are fixed at run time.

The user's own statement of the goal, in their words: "I want to see overarching topics that are coming in and people are publishing, and then I also want to see how different topics connect." Two questions, then:

1. **What is arriving.** Which broad topics are new or growing, measured by what people actually publish, and which small fast-growing sub-clusters sit inside each broad topic (new fields start small inside old ones: world action models inside robot learning, agent harnesses inside LLM agents).
2. **How topics connect.** Which topics are linked, where links are forming, and what the evidence for each link is.

The user chose the meaning of "connect" as a mix of two measurable things: **bridge papers** (papers whose nearest neighbours in the 768-d embedding space split between two topics) and **shared rising phrases** (one rising phrase appearing in papers of two topics). Convergence over time (topics moving toward each other across months) is a later addition, not v1.

Ruled out during the session: a "thinking desk" with the user's own notes on the map, a vault-on-the-map ingest, and taste learning from rated ideas. The user redirected to the two questions above; the home field becomes optional ("connections near me"), not the centre.

## What Makes This Cool

- One screen holds all of CS: 459k points, coloured by growth over a window you choose, with the 116 topics drawn as nodes and the links between them drawn as edges whose width is the size-normalised bridge strength (raw bridge counts shown as evidence). Thick edges that did not exist a year ago are the fields merging in front of you.
- Every link is clickable and shows its evidence: the bridge papers and the phrases both sides share. No link is an opinion.
- Any region you lasso becomes a first-class object with the same tools as a topic: growth, top papers, distinctive phrases, links to other topics, and "ideas between this and that".

## Constraints

- Local, single user, one process on the laptop (32 GB, Apple Silicon). No cloud, no login. The server listens on localhost only.
- Pipeline stays as is (`run_all.sh`: harvest, enrich, signals, backtests, HN, map, merge, report); the workbench reads what it writes. Map stage is 7 minutes and 8.1 GB peak at full size.
- DuckDB allows one writer process per file. The server opens `data/radar.duckdb` read-only and writes only `data/workbench.duckdb`, which the pipeline never opens; the pid-file rule in Part 2 keeps the pipeline and the server from running at the same time.
- Honesty rules carry over: the phrase signal is a modest predictor (pooled backtest: top-50 phrases grew 1.5x faster than CS in 36% of cases vs 27% baseline); category pairs are descriptive only; every growth number shows its window and baseline.
- Standard library first (ponytail mode): Python `http.server` over DuckDB; the page is one HTML file loading deck.gl from a CDN; no build step, no framework.
- Language model calls go through `claude -p` (existing `radar/llm.py`), subscription-billed, with all tools disabled, because the prompt carries untrusted paper text.

## Premises

1. Topics are the map's medium level (116 clusters) grouped under the coarse level (20); "arriving" is shown as growth per topic plus flagged fast-growing fine clusters (368) inside each topic.
2. A link between two topics is evidence computed in the pipeline and stored: bridge papers and shared rising phrases. The page only draws.
3. The nearest-neighbour graph is free: UMAP already computes a 15-neighbour cosine graph over all embedded papers in the map stage; keeping it costs storage (about 6.9 million rows), not compute.
4. Everything is a selection: a set of paper ids. Topic, fine cluster, lasso region, phrase, search result and saved home field are all selections, and every feature (stats, growth, top papers, distinctive phrases, links, ideas) acts on a selection. Distances are computed on the 768-d vectors, never on the 2-D layout.
5. Local only, no server beyond localhost; hosting is a later decision with its own cost (about €8 per month plus API calls, estimated on 2026-11-06).

## Approaches Considered

### Approach A: Static topic graph + growth map, generated by the pipeline

One new stage writes links and growth tables; one page like `merge.html` draws nodes at map centroids and edges by bridge count, click-through to papers. No server. Rejected by the user in favour of B: fixed window per run and no free selection.

### Approach B: Local server + live workbench (chosen)

Python standard-library HTTP server over DuckDB, one page with deck.gl, selections of any kind, time window slider, links overlay, inspector, ideas on demand. Approach A's stored tables are a strict subset of what B stores.

### Approach C: Monthly atlas

One generated page per coarse topic with sub-clusters, sparklines, links out, bridge papers and phrases, plus an index of what moved. Rejected: links across pages are harder to see than in one graph; no single picture of the whole.

## Recommended Approach

Approach B, in two parts.

### Part 1: pipeline additions (new stage `links`, after `map`)

New tables in `data/radar.duckdb`:

| table | columns | source |
|---|---|---|
| `knn` | `id, nbr, rank` (14 rows per paper) | UMAP's neighbour graph over the 768-d vectors (cosine), saved by `radar/map.py` instead of discarded; the self-neighbour at rank 0 is dropped, so each paper has 14 neighbours |
| `paper_topics` | `id, level, cluster, nbr_share` | from `knn` joined to `topic_members`: for each paper, the share of its 14 neighbours in each cluster |
| `bridges` | `id, level, c1, c2, share1, share2` | papers with at least 4 of 14 neighbours in a second cluster at the same level (threshold calibrated in Part 1, see Open Question 1) |
| `topic_links` | `level, c1, c2, month, n_bridge` | monthly counts of bridge papers per pair, so the page can compute any window |
| `phrase_topics` | `phrase, level, cluster, n, share` | rising phrases (S3, latest live run) counted per cluster by a literal match on title + abstract; `share` = this cluster's part of the phrase's papers |
| `topic_months` | `level, cluster, month, n` | monthly paper counts per cluster (growth for any window without a query) |
| `topic_onset` | `level, cluster, onset_month` | the month in which the cluster reached 10% of its papers (robust to a few old papers reassigned into it) |
| `paper_terms` | `id, term` | each paper's terms from the S3 candidate vocabulary (2 to 4 word phrases that passed the count filters, about 20,000 terms); used for distinctive-term queries without touching abstract text |

**Link strength and link growth (the numbers the page draws):**

- Raw bridge counts grow with cluster size and favour big neighbouring clusters, so edge width uses a size-normalised strength: `strength = n_bridge(c1, c2) / sqrt(n1 * n2)` over the chosen window, where `n1`, `n2` are the two clusters' paper counts in the same window. The raw count stays visible as evidence. Part 1 calibrates the bridge threshold and checks the top-ten edges against known pairs (robot learning and diffusion models should link; graph algorithms and medical imaging should not).
- Link growth is the bridge share `n_bridge / (n1 + n2)` in the window divided by the same share in the prior window, so two topics that both grow in volume do not show a "forming" link unless bridges grow faster than the topics. The links panel shows both shares. Minimum support: a growth ratio is computed only when the current window has at least 10 bridge papers; the prior share gets a pseudo-count of 1 bridge (`(n_bridge_prior + 1) / (n1_prior + n2_prior + 1)`) so a prior window with zero bridges gives a large finite ratio instead of a division by zero; a pair with at least 10 bridges now and fewer than 3 in the prior window is labelled "new" in the Links tab instead of showing a ratio.
- A shared phrase links two clusters only when the phrase has at least 10 papers in each cluster and at least 20% of its papers in each, and the phrase spans at most 4 clusters at the 20% level; broader phrases (for example "llm agents") are shown in the Phrases tab but draw no edge. Phrase links are a separate edge type (dashed), never added into bridge strength, so the two kinds of evidence stay distinguishable.
- Windows use complete months only: the current partial month is excluded, and every window label shows its last complete month.
- A fine cluster is flagged as "arriving" inside its topic when its `onset_month` falls inside the chosen window, it has at least 30 papers in the window, and its growth over the window is at least 2x after the CS-wide correction, with the prior count smoothed by a pseudo-count of 1 paper (`(n_now + 1) / (n_prior + 1)`); a cluster with at least 30 papers now and fewer than 5 before is labelled "new" rather than given a ratio; "new" is a display label for a flagged cluster, so the onset condition still applies. Part 1 checks the rule on known examples (world action models, agent harnesses) and adjusts the 10% onset share if they are missed.

Also stored at run time: `report/points.bin`, a binary file the page loads once (about 8 MB): for each embedded paper, in a fixed row order, x, y (float32), month index (uint16), primary category index (uint8), and cluster id at each of the three levels (int16). A sidecar `report/points.ids` (arXiv ids, one per line, about 4.6 MB) and a table `point_index(row, id)` in the database give the row-to-id mapping, so the browser sends row indices and the server turns them into paper ids.

### Part 2: server and page

`radar/serve.py` (standard library `ThreadingHTTPServer`, localhost:8765). The pipeline database `data/radar.duckdb` is opened read-only; each request uses its own cursor (`con.cursor()`), because one DuckDB connection must not be shared across threads. The two tables the server owns, `selections` and `ideas`, live in a separate file `data/workbench.duckdb`, so a pipeline rerun never touches them. A saved selection stores paper ids (never cluster ids, which change between map runs) plus the lasso polygon for display; its label and stats are recomputed on load. Lock rule: `serve.py` writes its pid to `data/serve.pid` and removes it on exit; `run_all.sh` writes its pid to `data/run.lock` and removes it with `trap 'rm -f data/run.lock' EXIT`, so a killed run does not leave the lock behind. Each side refuses to start while the other's pid file names a live process; a pid file whose process is dead is stale: the starter prints a warning naming the file, removes it, and continues. Liveness also checks the process command name (`radar.serve` or `run_all.sh`), so a reused pid after a reboot is not mistaken for a live lock; the manual fix is to delete the pid file. Writes to `workbench.duckdb` from handler threads go through one connection behind a lock. Request guard: every request must carry `Host: localhost:8765` or `127.0.0.1:8765`, and every POST must carry an `Origin` of the app's own address, otherwise 403; this stops other pages open in the same browser from triggering writes or language model calls. Memory: the server loads the 768-d vectors once at start (459,249 x 768 float32, about 1.4 GB) for centroid and distance queries; start-up is about 10 seconds. Endpoints, all JSON unless noted:

- `GET /points.bin`, `GET /points.ids`: the binary file and the id sidecar above. `GET /labels?level=`: cluster names and centroids.
- `GET /topics?from=&to=`: per topic: n, recent, prior, growth (CS-corrected, complete months only), and the fine sub-clusters flagged as arriving by the onset rule in Part 1.
- `GET /links?level=&from=&to=`: per pair: strength, raw bridge count, bridge share in the window and in the prior window, link growth; phrase links listed separately (phrase links are whole-corpus and do not follow the window; bridge links do). In the Links tab, "new" pairs sort first, then pairs by link growth; pairs with fewer than 10 current bridges show their raw count, no growth value, and sort last.
- `POST /select`: body is `{rows}` (row indices from a click or a lasso; the browser does the point-in-polygon test and sends only indices) or `{phrase}` (papers whose title or abstract contains the phrase, a literal match) or `{query}` (title search with DuckDB `ILIKE`; semantic search of free text is out of scope for v1 because no local text embedder is installed). Returns a selection id plus stats: n, monthly counts, growth, top cited and newest papers, distinctive terms (a DuckDB aggregate over `paper_terms`: only terms present in at least 3 papers of the selection and at least 1% of it are ranked, by `log((share_in_selection + 0.001) / (share_in_all_papers + 0.001))`, so one-off terms cannot top the list; selections over 20,000 papers use a random 20,000 sample for this one query), and links to topics (from `paper_topics` of its members).
- `GET /distance?a=&b=`: cosine distance between the 768-d centroids of two selections, overlap count, bridge papers between them.
- `POST /ideas`: `{a, b, n}`. The language model sees at most 28 papers: up to 8 bridge papers between A and B, plus the 5 most cited and 5 newest from each side, each with its arXiv id, title and a 400-character summary (about 6,000 tokens). The prompt is the one from `radar/merge.py`. After the call the server parses every `arXiv:ID` in the idea text; an idea that cites an id outside the shown set, or cites fewer than one paper from each side, is regenerated once (the single idea, not the whole call) and dropped if it fails again, and the drop is logged. The model call runs outside any database cursor. Ideas are stored with both selection ids and the shown paper ids.

Notes on selections or ideas are not in v1; they belonged to the "thinking desk" the session ruled out.

`radar/app.html`: one page, three columns.

```
controls            | map                                        | inspector
time window         | 459k points (deck.gl ScatterplotLayer)     | selection A / B
level: 20/116/368   | labels for the chosen level                | n, monthly bars, growth
colour by: topic |  | links overlay: nodes at centroids, edges   | distinctive phrases
  growth | date |   |   width = bridge strength, colour =      | top cited / newest
  category | dist A |   growth of bridges; click edge → evidence | rising phrases inside
search / phrase     | lasso tool, click topic                    | links to other topics
A = [saved ▾] B = … | tabs: Topics table | Links table | Phrases | A vs B: distance, overlap
                    |       | Ideas                              | [Ideas between A and B]
```

"Colour by growth" colours each point with the growth of its cluster at the chosen level over the chosen window; growth is a cluster property, not a paper property. "Colour by distance to A" colours each point by the cosine distance of its fine cluster's centroid to A's centroid.

- "What is arriving" lives in the Topics tab (sortable by growth, with the flagged sub-clusters shown under each topic) and in colour-by-growth on the map.
- "How topics connect" lives in the links overlay and the Links tab (sortable by bridge count and by bridge growth); clicking a link shows its bridge papers and shared phrases.
- The home field is one saved selection among others; "distance to A" colouring and the Ideas button use whatever A is.

### Honesty in the page

Every growth number shows "last N complete months vs the N before, corrected for CS growth" with the last complete month named. The links panel states the bridge definition, the threshold, the normalisation (strength and bridge share) and the phrase-link rule. The Phrases tab shows the pooled backtest line (36% vs 27%). Category pairs are not shown in the workbench at all.

### Why not the alternatives

A static page (Approach A) would answer both questions for one window and lose nothing stored, but the user chose free selection and a movable window. The atlas (C) reads well but hides links across pages.

## Open Questions

1. Bridge threshold: 4 of 14 neighbours in a second cluster is a guess. Calibrate on known pairs (robot learning and diffusion models should link; graph algorithms and medical imaging should not) during Part 1, using the normalised strength, not raw counts.
2. deck.gl at 459,249 points with per-point colour updates has only been seen at 60,000 points in datamapplot. Part 2 step 1 measures redraw time; fallback is to colour at the topic level only, or to draw a 150k sample while stats use all papers.
3. Should "arriving" also surface fine clusters that are new this quarter but small (under 137 papers, the current fine minimum)? Probably needs a fourth, finer level or a phrase-first view; deferred.
4. Does the kNN graph from UMAP (built on all 459k points with `low_memory=True`) have enough precision for bridges, or should bridges use an exact k-nearest search on the 768-d vectors for a sample? Check on 1,000 random papers in Part 1.
5. Time-lapse (convergence over months) needs aligned maps across runs; UMAP is not stable between runs. Out of scope for v1; `topic_links` by month keeps the door open for a link-growth view without re-laying out the map.

## Success Criteria

- Open `http://localhost:8765`, pick "last 6 months", colour by growth, and name the five fastest-growing topics and their flagged sub-clusters without reading the report.
- Turn on links; the ten thickest edges are pairs a CS researcher would accept as real (no edge between unrelated fields in the top ten), and each click shows at least 5 bridge papers.
- Lasso the gap between two clusters; the inspector returns stats, top papers and distinctive phrases in under 3 seconds.
- "Ideas between A and B" returns ideas whose cited arXiv ids are all in the shown set (checked by the server, not only asked of the model), stored and visible in the Ideas tab after a restart, and still present after a pipeline rerun.
- The map renders and pans at full size in Chrome or Safari on the laptop without stalls over 1 second (measured in Part 2 step 1).

### R3-1 — clarity (minor)

**Problem**

> The new sentence about pid files being 'owned by workbench.duckdb's side' is garbled. Pid files and DuckDB files are unrelated, and the sentence makes the lock rule harder to read without adding a decision.

### R3-2 — feasibility (minor)

**Problem**

> The liveness check only tests whether a pid is alive. After a crash or reboot the old pid can belong to an unrelated process, so a stale lock looks live and blocks start-up. Check-then-write also leaves a small race if both are started at once. Single-user risk is low.

**Remedy**

> When checking liveness, also check the process command name (python radar.serve / run_all.sh). Optionally create the pid file with O_EXCL, or document the manual fix (delete the file).
