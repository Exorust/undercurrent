## Merge ideas

Written by an LLM from 5 papers per topic. Treat each as a prompt for your own thinking, and check the cited papers.

### Embodied Planning and Robot Benchmarks
*cosine distance from home field 0.04, topic growth x2.1*

Hierarchical planning with latent world models (arXiv:2604.03208) plans over several time scales using only a learned next-state predictor, and it reports up to 3x less planning compute on long-horizon tasks. The same structure could help a coding agent harness, which now makes long chains of tool calls (edit, build, run a GPU kernel, profile) and spends most of its cost on failed attempts. Treat a Metal or CUDA kernel tuning session as the environment: the latent state is the kernel source plus its profiler counters (occupancy, memory bandwidth, register use), and a small world model, perhaps a fine-tuned small language model, predicts how counters and runtime change after each edit. A high-level planner would pick a sequence of edits, such as tile size, then memory layout, then vectorization. The low-level step would run only the top candidates on real hardware. The fit is plausible because kernel tuning has the same shape as long-horizon manipulation: actions are costly, the outcome is delayed, and a cheap learned model can screen out poor plans. The benchmark side matters too, since arXiv:2602.08971 argues world models should be scored on how useful they are for the task, not only on how accurate their predictions look. That suggests judging this model by how much real benchmarking time it saves. First experiment: log a few thousand (kernel edit, profiler counters, runtime) triples from an existing Metal kernel autotuning loop on Apple silicon. Then train a small predictor on them and compare "plan with the predictor, run the top 5" against random and greedy search at the same count of real hardware runs.

### Vision-Language-Action Robot Policies
*cosine distance from home field 0.06, topic growth x2.0*

Draw the "soft prompt per data source" idea from X-VLA (arXiv:2510.10274) into the home field's coding agents. An agent harness for Metal and CUDA kernel work sees many different "embodiments": each GPU target (Apple M-series, NVIDIA SKUs) has its own compiler quirks, memory limits, and timing behavior. Today a small on-device model is usually prompted or fine-tuned per target, or just given one generic prompt, and it does poorly on targets it saw little data for. X-VLA shows that a small set of learnable embeddings, one per data source, lets a single shared transformer absorb heterogeneous data with few added parameters, and that fits kernel generation because the target differences are mostly systematic, not semantic. A second source of ideas is Fast-WAM (arXiv:2603.16666), which finds that video prediction helps mainly as a training signal, not as test-time imagination. The kernel analogue is to train a small language model with an auxiliary "predict the profiler trace" loss, then skip trace prediction at inference, so you get the benefit without extra latency on-device. First experiment: take a small open code model (1-3B), add one learnable soft-prompt embedding per hardware target, and fine-tune on existing kernel-plus-benchmark pairs from Metal and CUDA. Compare compile-and-correctness rate and speedup on held-out kernels against a single-prompt baseline and per-target full fine-tunes, including a leave-one-target-out test to see whether a new target's embedding can be fit from a few examples, as in the cross-embodiment setting of arXiv:2506.09985's low-data robot adaptation.

### Fair Allocation and Mechanism Design
*cosine distance from home field 0.08, topic growth x1.8*

Maximin share (MMS) approximation, the rounding and matching techniques from papers like arXiv:2511.13056 and arXiv:2506.05613, could be used to split a fixed on-device memory and compute budget among competing tasks in a small-language-model coding-agent harness. Today, a harness on Apple Silicon usually divides unified memory, KV cache (the stored attention state for earlier tokens), and GPU time between parallel subagents, tool calls, and kernel-tuning jobs by hand-set quotas or first-come-first-served. Those resources are indivisible in practice (a cache page or a GPU dispatch slot is either held or not), and the tasks value them very differently. The task requirements are not additive, because two kernel variants may share a cached prefix. That makes the subadditive-valuation results in arXiv:2506.05613 a closer match than the additive case. The guarantee that matters is "each task gets at least a fixed fraction of the best share it could have secured if it split the pool itself", which prevents one long-running task from starving the others. For a first experiment, replay logs of a multi-subagent coding session on an M-series Mac with a 3B to 8B model, and compare three allocators: static equal quotas, greedy first-come-first-served, and a 7/9-style MMS approximation like the one in arXiv:2511.13056. Measure the worst-off task's completion rate and the total tokens per second. If the MMS allocator does not improve the worst-off task without a clear throughput loss, the idea should be dropped.

### Cloud, GPU and Storage Infrastructure
*cosine distance from home field 0.04, topic growth x1.5*

Astra's multi-agent loop (arXiv:2509.07506) and AccelOpt's self-improving loop (arXiv:2511.15915) both optimize CUDA or accelerator kernels with LLM agents, but they assume datacenter GPUs and a large model. The home-field problem is that Metal kernels for Apple silicon have little public tuning knowledge, and a small on-device model has to run the optimization itself. The fit is plausible because AccelOpt is built to work on new accelerators without expert hardware knowledge, which describes Metal well, and its self-improving memory of past kernel rewrites could be small enough for a small model to use. A serving-side idea from arXiv:2507.10150 also applies: it plans around peak memory instead of average memory, and on a unified-memory Mac a long agent session sharing RAM with the kernel benchmarks has the same risk of running out. The first experiment is to port the AccelOpt loop to Metal. It would take 20 to 30 standard kernels, such as softmax, layernorm, and attention, from MLX or llama.cpp, and use a 3B to 8B local model as the optimizer. It would compare speedup over the baseline kernel against the same loop driven by a large hosted model, and record peak memory and wall-clock time per accepted rewrite.

### Speech Recognition and Diarization
*cosine distance from home field 0.06, topic growth x1.5*

Speech-aware language models still fail at the thing a coding agent needs most: following a precise instruction without drifting. arXiv:2505.19037 measures this directly, showing that adding speech ability causes catastrophic forgetting of instruction-following. The idea is to take the long-form, multi-speaker transcription approach of arXiv:2601.18184 (VibeVoice-ASR) and run it as a small on-device speech front end for an Apple Silicon coding agent, so a developer can talk through a task and have the agent harness receive text with speaker turns and timestamps. The fit is plausible because the recent Speech-IFEval-style evaluations (arXiv:2505.19037) show that a small speech-aware model can lose instruction-following ability. A cascade, where ASR produces text and a small text-only language model keeps the coding behavior, avoids that loss, and it also fits within the memory and kernel budget of a Metal-based on-device stack. The first experiment is to run a quantized ASR model on a Mac through a Metal backend and feed its transcripts, from a recorded 20-minute two-person pairing session, into an existing coding agent. Then compare task success and latency against typed prompts, and against a single end-to-end speech-aware model scored with the instruction-following protocol from arXiv:2505.19037. Report word error rate, time to first token, and peak memory, and check whether diarization errors, such as a task assigned to the wrong speaker, are what cause the failed agent runs.

### Music and Audio Generation
*cosine distance from home field 0.07, topic growth x1.5*

Neural audio codecs with very low frame rates, such as FlexiCodec (arXiv:2510.00981), could shrink the context cost of audio input for small on-device language models. Today, a small model on Apple Silicon that must handle speech or sound, for example a coding agent that takes voice commands or listens to build and test alerts, pays a large token and memory price for each second of audio. A dynamic-rate codec keeps semantic content while spending fewer tokens on silence and repetition, which makes the fit plausible for tight memory and latency budgets. Audio Flamingo Next (arXiv:2604.10905) shows that audio-language models can reason over speech, sound and music, but at a scale that does not run locally, so a compact codec front end is the missing piece. The DCASE 2025 task (arXiv:2506.10097) also reports that small models trained from scratch can compete with large pre-trained ones, which suggests a small audio path is workable. First experiment: write a Metal kernel for the FlexiCodec decoder and encoder, run it with a 1B-parameter model on an M-series Mac, and measure tokens per second of audio, end-to-end latency and peak memory, then compare word error rate and sound-event accuracy against a fixed-frame-rate baseline codec.

### Efficient Transformer Architectures
*cosine distance from home field 0.04, topic growth x1.4*

Mixture-of-Recursions (arXiv:2507.10524) lets a small transformer reuse one shared block a variable number of times per token, so easy tokens exit early and hard tokens get more depth. The home-field problem it could address is decode latency and memory for small on-device language models on Apple Silicon: a shared block means the weights are loaded once, which matters when memory bandwidth is the bottleneck. The fit is plausible because per-token routing only pays off if the kernels can handle ragged batches, and that is a kernel problem the researcher already works on. The stable looped design in arXiv:2604.12946 gives a recipe for training looped models without divergence, so the shared block can be iterated safely at inference. As a hardware-friendly alternative to routing, arXiv:2603.15569 shows that a state space recurrence can cut decode cost without a quality loss, and it provides a baseline for comparison. The first experiment is to write a Metal kernel that runs a shared transformer block with per-token early exit (grouping tokens by remaining depth to keep the GPU busy). Then measure tokens per second and memory traffic against a standard non-recursive model of the same parameter count on an M-series chip.

### Multi-Agent Robot Planning and MPC
*cosine distance from home field 0.07, topic growth x1.3*

Use a sampling-based model predictive control (MPC) planner, as in the multi-agent UAV formation work in arXiv:2508.21316, to choose the next action in a coding agent harness. Today, harnesses on small on-device models usually commit to one greedy tool call per step, so one bad edit can cost several turns to undo. Treat each step as a short-horizon control problem: sample a few candidate actions (edit, run test, read file), score them with a cheap cost function (test pass count, diff size, compile errors), execute only the first action of the best plan, then re-plan. The fit is plausible because arXiv:2508.21065 shows that fast online adaptation of a policy works when you have a cheap, differentiable or at least fast simulator. Here the "simulator" is a sandboxed build and test run, which on Apple Silicon with Metal kernels is quick enough to roll out several branches. The nano-drone deployment work in arXiv:2607.12593 also shows the same constraint, a small compute budget with tight latency, so its approach of automated end-to-end optimization of the deployed model is a useful guide for budgeting how many rollouts a small model can afford. First experiment: take 50 small bug-fix tasks from an existing coding benchmark, run a 3 to 4 billion parameter local model with the greedy harness versus a 3-candidate, depth-2 MPC harness, and compare pass rate and wall-clock time per task.
